# 04 — x402 comparison route

Add an x402 payment path beside the MPP one (`/api/pay`, increments 02–03)
so the two protocols can be compared against the same store, the same
product, and the same amount. This is the template's most valuable asset —
keep both paths structurally parallel so the protocol difference is the only
variable a reader sees.

## Verified against the live facilitator, 2026-09-22 and re-confirmed 2026-09-23

```
$ curl -s https://testnet.facilitator.ax402.io/supported
{"kinds":[
  {"x402Version":1,"scheme":"exact","network":"eip155:84532"},
  {"x402Version":1,"scheme":"exact","network":"eip155:114"},
  {"x402Version":1,"scheme":"exact","network":"eip155:5042002"},
  {"x402Version":1,"scheme":"exact","network":"eip155:12227332"},
  {"x402Version":2,"scheme":"exact","network":"eip155:84532"},
  {"x402Version":2,"scheme":"exact","network":"eip155:114"},
  {"x402Version":2,"scheme":"exact","network":"eip155:5042002"},
  {"x402Version":2,"scheme":"exact","network":"eip155:12227332"},
  {"x402Version":2,"scheme":"batch-settlement","network":"eip155:84532","extra":{"receiverAuthorizer":"0xf76B..."}},
  {"x402Version":2,"scheme":"exact","network":"hedera:testnet","extra":{"feePayer":"0.0.9839454"}}
],
"extensions":[],
"signers":{"eip155:*":["0xf76B..."],"hedera:*":["0.0.9839454"]}}
```

**The Hedera network identifier is `hedera:testnet`, not `eip155:296`.** The
facilitator uses a CAIP-2-style namespace for Hedera and `eip155:` chain ids
for its EVM networks (Base Sepolia `eip155:84532`, Flare Coston2 `eip155:114`,
and two others). Passing a chain-id form silently never matches an entry in
`kinds` — that gets debugged as a payment bug, not a wrong constant. Match on
the pair `{ scheme: "exact", network: "hedera:testnet" }` (x402Version 2).

Endpoint responded HTTP 200 in under a second both times it was checked. No
client SDK for x402 or Ax402 is installed in this workspace (`node_modules`
has no `x402`-named package) — there is nothing to import; requests are
built by hand against the shapes below.

## Facilitator capability, not a hardcoded list

`AX402_FACILITATOR_URL` already exists in `lib/demo.ts`'s `hasX402()` and in
`.env.example`, empty by default — the rail is off with no environment set,
matching `hasHedera()`/`hasStripe()`. Leave `hasX402()` exactly as-is; it is
the same kind of synchronous, env-only gate the other two predicates are, and
nothing here should make it async or add network I/O to it.

Add `lib/x402.ts` for everything that does need network I/O:

- A memoized async `x402Capability()` that, only when `hasX402()` is true,
  fetches `${process.env.AX402_FACILITATOR_URL}/supported` (use `fetch` with
  `AbortSignal.timeout(3_000)` or similar — do not let a slow third party
  hang a request) and resolves to
  `{ live: true }` when the response is 200 and its `kinds` array contains an
  entry with `scheme === "exact"` and `network === "hedera:testnet"`, or
  `{ live: false, reason: string }` for anything else: non-200, timeout,
  network error, malformed JSON, or the pair simply absent from `kinds`
  (the facilitator is reachable but doesn't currently support Hedera).
  **Never throw** — every failure mode resolves, it never rejects.
- Cache the resolved promise at module scope so the first caller pays the
  network round trip and every later call in the process is free. This is
  the "confirm at startup" requirement: not a blocking top-level `await`
  (which would stall module evaluation and, transitively, dev-server
  compilation of anything importing this module), but a check performed on
  first use and reused for the life of the process — the same lazy-once
  shape `stripeClient` in `lib/mppx.ts` already uses for its own
  credential-gated setup.
- `canSettleX402()`: `async () => hasX402() && (await x402Capability()).live`.
  This is the one thing route code should call; it folds "credentials
  configured" and "facilitator actually supports Hedera right now" into one
  answer.

A third-party endpoint being down must never crash the app: if
`AX402_FACILITATOR_URL` is set but the facilitator is unreachable or drops
Hedera support, `canSettleX402()` resolves `false` and the route below
degrades to its demo response — it does not 500, and it does not affect
`hasHedera()`/`hasStripe()`/`/api/pay` in any way (per-integration, never
global, same rule `lib/demo.ts` already documents).

## Separate endpoint, deliberately

Unlike Stripe, x402 is a different protocol, not another MPP method — it
does **not** go into the `methods` array in `lib/mppx.ts`, and it does not
touch `Mppx.create()` or `/api/pay` at all. It gets its own route:
`app/api/x402/route.ts`, handling `GET /api/x402?product=<id>` (mirror
`/api/pay`'s query param: unknown or missing id falls back to `products[0]`,
never 404s, so the route is always inspectable on its own).

The checkout page already lists x402 as a third `PaymentOption` gated on
`hasX402()` (see `app/checkout/page.tsx`) with no custom `action`, so it
already renders the generic disabled "Pay with x402" button and the
"demo mode" note with `AX402_FACILITATOR_URL` named as the variable to set —
this already matches how the Stripe rail behaves and needs no changes here.
Leave it alone unless you find it broken.

## The challenge shape

On a request with no `X-PAYMENT` header, respond `402` with a body shaped
like the x402 spec's payment-required response — this is what makes the
comparison legible; an agent or a reader should be able to look at
`/api/pay` and `/api/x402` side by side and see the same offer expressed in
two protocols:

```json
{
  "x402Version": 2,
  "error": "X-PAYMENT header is required",
  "accepts": [
    {
      "scheme": "exact",
      "network": "hedera:testnet",
      "maxAmountRequired": "<product price, USDC base units, as a string>",
      "resource": "https://<host>/api/x402?product=<id>",
      "description": "MPP Checkout — <product name>",
      "mimeType": "application/json",
      "payTo": "<chargeRecipient() from lib/mppx.ts>",
      "maxTimeoutSeconds": 60,
      "asset": "<USDC_TOKEN_ID from lib/mppx.ts>"
    }
  ]
}
```

Reuse `chargeRecipient()` and `USDC_TOKEN_ID` from `lib/mppx.ts` rather than
re-deriving them — same recipient, same token as the Hedera rail, so the
only thing that differs between `/api/pay` and `/api/x402` is the protocol
envelope. Compute `maxAmountRequired` from `product.priceUsd` and
`USDC_DECIMALS` (also exported from `lib/mppx.ts`) as a **string built from
the decimal digits**, not `Number(priceUsd) * 10 ** decimals` — this
codebase's rule against float arithmetic on money (see `AGENTS.md`,
`lib/products.ts`'s comment on decimal-string prices) applies here exactly
as it does to the Hedera and Stripe rails.

Send `demo: true` alongside `accepts` in the body, and header
`X-MPP-Demo-Mode: x402`, whenever `canSettleX402()` is false — matching
`/api/pay`'s existing `X-MPP-Demo-Mode` header, so a client (or a judge)
inspecting either endpoint sees the same convention for "this challenge is
real but nothing behind it can settle yet." The `accepts` entry itself stays
well-formed and inspectable in demo mode; only the settlement path behind it
is stubbed.

For `Accept: text/html` in demo mode, render a plain, disabled panel — same
product, same amount, same "demo mode" badge, same style as
`renderStripeDemoPanel` in `app/api/pay/route.ts`. Do not attempt to
literally reuse that function (it's Stripe-shaped and private to that file);
a small x402-flavored equivalent in the new route is fine, and should look
and read like it belongs next to it.

## Settling a real payment — timeboxed

Actually verifying a submitted `X-PAYMENT` header (calling the facilitator's
`POST /verify` and `POST /settle`, and getting a buyer's wallet to produce a
payload the "exact" / `hedera:testnet` scheme accepts in the first place) is
real integration work against a protocol this workspace has no prior code
for: no installed client library, no confirmed payload shape for Hedera's
`exact` scheme beyond the `{scheme, network, extra.feePayer}` triple above,
and no existing browser-side signing flow to reuse the way
`HederaPayButton`/`useHederaSigner` already do for the native rail.

**If this exhausts the attempt budget, stop at the honest challenge +
demo-mode route above and ship that.** A route that issues a spec-correct,
inspectable `402` and degrades honestly when the facilitator can't be used
is a complete and honest deliverable on its own — the comparison document
(this PRD, plus a short section in `AGENTS.md`'s route table and conventions
noting x402 is wired for the challenge side and documented rather than fully
settled) is worth more than a partially-working third rail with a signing
flow half-built into the UI. The deadline is not negotiable; MPP (Hedera +
card) fully working is the floor this increment must not regress.

If there is budget left after the challenge route is solid, and only then,
attempt real settlement:

- Accept `X-PAYMENT` (base64-encoded JSON payment payload, per the x402
  convention `/api/pay` and Stripe's SPT flow both echo in spirit) on the
  retried request.
- `POST {AX402_FACILITATOR_URL}/verify` then `POST {AX402_FACILITATOR_URL}/settle`
  with `{ x402Version: 2, paymentPayload, paymentRequirements }` (the same
  `accepts[0]` object served in the 402). Treat both as fallible network
  calls with the same timeout/never-throw discipline as `x402Capability()`.
- On a settled response, record a `SettledOrder` via `recordOrder()` in
  `lib/orders.ts` with `method: "x402"`, and extend `/receipt/[id]`'s
  `isCard` boolean (`app/receipt/[id]/page.tsx`) into a method-keyed switch
  over `"hedera" | "stripe" | "x402"` so an x402 receipt's amount units and
  "Payment rail" label render correctly — this is the "same receipt view"
  requirement, and it only needs touching if a real x402 order can actually
  reach it.

If you stop at the challenge route (the expected outcome given the timebox),
leave `lib/orders.ts` and the receipt page untouched — there is nothing for
them to record, and speculative branches for a method that never settles
are worse than not having them.

## Out of scope

Mainnet facilitator URLs — testnet only, matching every other rail in this
template. Modifying `lib/mppx.ts`'s `methods` array, `/api/pay`, or anything
under the Stripe rail. A browser-side x402 signing flow / new
`X402PayButton` component — the existing generic disabled `PaymentOption`
button already renders the demo-mode state correctly; building a live payer
UI is part of the same timeboxed settlement work above, not a separate
requirement.
